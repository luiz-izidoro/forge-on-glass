## 0. Sumário executivo

Ao auditar o projeto eu não parei na leitura dos documentos — reproduzi o último
build na VM e **derrubei o muro que estava documentado como bloqueador**.

O que a documentação dizia: *"resta um crash do compilador 6.3.3 no SILGen
(emitCBridgedToNativeValue) — sem linha exata"*.

O que era de fato:

| # | Diagnóstico anterior | Realidade encontrada | Correção |
|---|---|---|---|
| 1 | "crash do compilador" | `note: IO failure on output stream: **Disk quota exceeded**` na última linha do log — o `/tmp` da VM é **tmpfs de 1,9 GB** e o module cache (`-fmodules-cache-path=/tmp/impmc`) o encheu | mover cache para disco real (`~/bigtmp/impmc`) |
| 2 | "crash no bridging de algum stub patchado" | **Signal 11 real**, mas a causa não eram os stubs: são métodos `@objc` em **subclasses genéricas de NSObject** — só **3 classes** no interface inteiro | `patch_uikit_generic_objc.py` remove `@objc` de 25 membros |
| 3 | "`-Onone` talvez resolva; usuário cancelou o teste" | o teste com `-Onone` **nunca chegou a rodar**: falhava antes com `no such module 'SwiftOnoneSupport'` (faltava passar o `-swift-module-file`) | passar `SwiftOnoneSupport` explicitamente |

**Resultado obtido hoje, já validado:**

```
[swift:UIKit] OK 1032412B 5s          ← o módulo que estava "impossível"
CASE uikit_foundation  rc=0  obj=13576 B   ← import UIKit + import Foundation
CASE swiftuicore       rc=0  obj=4136 B    ← import SwiftUICore
```

`import UIKit` em Swift puro **compila e gera código objeto**. Restam: gerar o
módulo `SwiftUI` top-level, transportar tudo para o iSH e revalidar o pipeline
de IPA. Este documento é o plano para isso.

### 1.3 Dívidas técnicas descobertas nesta auditoria

1. **`/tmp` tmpfs de 1,9 GB na VM** — causou o falso "crash". Todo script novo deve
   apontar caches para `~/bigtmp`. *(mitigado hoje)*
2. **Jobs SSH morrem ao desconectar.** `nohup` **e** `setsid` falharam (testei os
   dois). Só **tmux** persiste. Isso explica builds "que sumiram" em sessões
   anteriores e provavelmente parte da lenda de "não determinismo".
3. **SDK patchado in-place na VM sem versionamento.** Os interfaces de trabalho
   estão modificados sobre a cópia da VM; o original está no iSH. Um `rm -rf`
   descuidado perde ~40 h de patches. → precisa de patch-set versionado (P1).
4. **Version-lock latente.** O SDK declara `interface-compiler-version 6.3.2`.
   No modo **implícito** o 6.3.3 é rejeitado com erro fatal; no modo
   **explicit-module** a checagem não dispara. Nossa pipeline só funciona porque
   é explícita — isso deve estar documentado, é uma restrição estrutural.

## 2. Pesquisa realizada (fontes e o que cada uma entregou)

### 2.1 swiftlang/swift (GitHub Issues)
- Busca `"compile-module-from-interface" "no type named"` → **2 resultados**:
  `#85495` (_GUID no WinSDK, fechado por `#86327`) e `#54220` (CoreMedia watchOS,
  aberto desde 2019). Confirma o que a sessão anterior já tinha achado: **o bug
  dos tipos reexportados não tem issue própria** — o projeto está em território
  inédito.
- Busca `emitCBridgedToNativeValue crash` → **0 issues**. O crash do SILGen com
  subclasse genérica `@objc` **não está reportado**. Isso vira oportunidade (P3):
  temos um repro mínimo de 6 linhas.

### 2.2 xtool-org/xtool — a referência mais valiosa
- `Sources/XToolSupport/SDKBuilder.swift` (513 linhas, lido na íntegra).
  **Achado decisivo:** o `isWanted` **exclui explicitamente**
  `Toolchains/XcodeDefault.xctoolchain/usr/lib/swift/**/prebuilt-modules`, e o
  `SDKEntry.wanted` **inclui** `Toolchains/XcodeDefault.xctoolchain/usr/lib/{swift,swift_static,clang}`.
  Ou seja: o xtool copia o `usr/lib/swift` **inteiro do Xcode** — que contém os
  `.swiftmodule` **binários** de UIKit, SwiftUI, Foundation etc. **Ele nunca
  recompila os interfaces.** É por isso que o xtool "simplesmente funciona" em
  Linux enquanto nós lutamos 3 dias: ele não resolve o problema, ele o evita.
- `Documentation/xtool.docc/Installation-Linux.md`: exige toolchain **6.3** —
  compatível com a nossa linha.
- Issue `#152` "Cross import overlays seem broken" (fechada por `#153`):
  **`import SwiftUI` + `import MapKit` não resolve `Map()`** sem
  `-Xfrontend -enable-cross-import-overlays`. → **Aplicável a nós**: quando o
  SwiftUI top-level entrar, esta flag será necessária. Anotado no plano (§3.2).
- Issue `#177` (unit tests) e `#93` (macOS target): confirmam que rodar/testar
  fora do device continua fora de alcance mesmo no projeto de referência.

### 2.3 kabiroberai/swift-sdk-darwin
README: **DEPRECATED**, sucedido pelo xtool. Exige macOS + Xcode + rsync para
gerar o bundle. Nosso `PROCEDIMENTO-MAC.md` aponta para ele → deve ser atualizado
para o fluxo `xtool sdk install` (P1/P2).

### 2.4 Inspeção do binário do compilador (fonte primária)
`strings swift-frontend | grep` revelou a mensagem exata do version-lock e a flag
`-Rskip-explicit-interface-build`. `-help-hidden` revelou o arsenal disponível:
`-prebuilt-module-cache-path`, `-backup-module-interface-path`,
`-disable-building-interface`, `-downgrade-typecheck-interface-error`,
`-blocklist-file`, `-sdk-module-cache-path`. **Duas destas são a base dos Planos
B e C abaixo** e nunca foram exploradas no projeto.

### 2.5 Auditoria do bundle do Mac
`/var/minis/shared/darwin-sdk/bundle/darwin.artifactbundle` contém **apenas**
`Developer/Platforms/` — **falta `Developer/Toolchains/`**, exatamente o diretório
que o xtool usa para pegar os módulos binários. O bundle foi gerado ou copiado
parcialmente. **Se o usuário rodar o `xtool sdk` no Mac de novo e trouxer o
`Toolchains/usr/lib/swift/iphoneos`, todo o problema de interface-compile
desaparece por construção** (Plano C, §5).

## 3. Plano de execução — Fase 1: fechar SwiftUI na VM (P0)

### 3.1 Pré-condições (aplicar sempre, são as lições de hoje)
```bash
# 1. tmux, SEMPRE (nohup/setsid não sobrevivem à queda do SSH)
tmux new-session -d -s <nome> "<comando> > /tmp/<nome>.log 2>&1; sleep 7200"
# 2. cache de módulos NUNCA em /tmp (tmpfs 1,9 GB)
mkdir -p ~/bigtmp/<nome>   # e substituir /tmp/impmc nos args
# 3. após cada build, checar o FIM do log, não só o grep de "error:"
tail -3 <mod>.err | grep -i "quota\|space\|Signal"
```

### 3.2 Passo 1 — compilar `swift_SwiftUI.swiftmodule`
O interface existe: `SwiftUI.framework/Modules/SwiftUI.swiftmodule/arm64e-apple-ios.swiftinterface`.
SwiftUICore (a parte pesada, 4 MB) já está compilado, então o top-level tende a
ser fino.

1. Adaptar `rebuild_uikit.py` → `rebuild_swiftui.py` (trocar `name = 'SwiftUI'`).
   Se `SwiftUI` não estiver no `/tmp/fscan.json`, rodar um scan novo com um
   `seed.swift` contendo `import SwiftUI` (receita em `scan633.sh`).
2. Erros esperados, **na ordem em que devem ser atacados** (os 8 mecanismos
   já mapeados em `ESTADO-E-NEXT-STEPS.md` §2 + o 9º descoberto hoje):
   - tipos reexportados → nome clang direto ou stub local;
   - `@objc` em subclasse genérica → **`patch_uikit_generic_objc.py` já é
     genérico, basta apontar para o novo interface**;
   - membros de extensão de outro módulo em corpo `@inlinable` → reescrever;
   - cross-import overlays (`_MapKit_SwiftUI` etc.) → **adicionar
     `-enable-cross-import-overlays`** (achado da issue #152 do xtool).
3. Validar com `test_import_uikit.py swiftui` (o caso já está escrito).

**Critério de aceite:** `CASE swiftui rc=0 obj>0`.

**Se travar > 4 h:** aceitar SwiftUI parcial. `import SwiftUICore` já entrega
`View`, `Text`, `Color`, layout e modifiers — 80 % do valor. Documentar e seguir.

### 3.3 Passo 2 — consolidar o patch-set (evita perder 40 h de trabalho)
Hoje os patches estão espalhados em 8 scripts (`patch_interface*.py`,
`patch_more.py`, `patch_unqual.py`, `patch_swiftuicore_master.py`,
`patch_uikit.py`, `patch_uikit_generic_objc.py`) **mais** edições manuais
in-place. Consolidar em **um** `apply_all_patches.py`, idempotente, que:
- recebe o caminho do SDK **original** (o do iSH é a fonte limpa);
- gera cópia de trabalho e aplica tudo em ordem determinística;
- valida com `sha256` esperado por interface e falha alto se divergir;
- gera `PATCHSET.md` com o diff resumido (para a auditoria legal do §PUBLISHING:
  strings-âncora de assinaturas de API, de-minimis).

**Critério de aceite:** partindo do SDK limpo, um único comando reproduz os 152
artefatos + UIKit + SwiftUI.

## 4. Fase 2 — trazer para o iSH e provar ponta a ponta (P0)

### 4.1 O problema de espaço (resolver ANTES de copiar)
```
iSH:  114 GB usados / 119 GB   →  5,0 GB livres   (96 %)
```
`foundation-build633` são ~160 MB (ok), mas manter **dois** toolchains
(`/opt/swift6.3` 3,3 GB + `/opt/swift6.3.3`) é o que aperta.

**Decisão recomendada:** após validar o 6.3.3 no iSH, **apagar `/opt/swift6.3`
(6.3.2) e `/opt/ios-toolchain/foundation-build`** → libera ~3,5 GB. Antes disso,
fazer backup do essencial (`exp63/modules`, `SwiftShims.pcm`) em
`/var/minis/shared/darwin-sdk/`.
**Não apagar nada antes do critério de aceite do §4.3 passar.**

### 4.2 Transporte
```bash
# VM
cd ~/swift-ios-build && tar czf ~/dl/fb633.tar.gz foundation-build633   # ~160MB → ~60MB
# iSH
scp $ISB_REMOTE_USER@$ISB_REMOTE_HOST:~/dl/fb633.tar.gz /tmp/
tar xzf /tmp/fb633.tar.gz -C /opt/ios-toolchain/ && rm /tmp/fb633.tar.gz
```
Depois, os symlinks que os `.pcm` exigem (já documentados em
`DISPATCH-VIA-LINUX.md`) — conferir se existem para o **6.3.3**:
```bash
/opt/swift6.3.3/usr/lib/swift/{dispatch,os,CoreFoundation} -> SDK   # crítico
${ISB_SYSROOT:-/opt/isb/sysroot}/{iPhoneOS26.5.sdk,swift-6.3.3}           # paths embutidos nos pcm
$SDK/.../CoreFoundation.framework/Headers/Modules/module.modulemap
rm -rf /root/.cache/clang
```

### 4.3 Validação end-to-end (o critério que declara vitória)
1. `test_import_uikit.py` (portado para o iSH) — casos `uikit_foundation`,
   `swiftuicore`, `swiftui`.
2. **Linkar** de verdade: adicionar `-lswiftUIKit`, `-lswiftSwiftUICore`
   (os `.tbd` existem em `$SDK/usr/lib/swift/`), `-framework UIKit`.
3. Gerar um **IPA completo 100 % Swift** (sem uma linha de ObjC) e passar no
   `validate-ipa.sh`: `platform ios / sdk 26.5`, links de `libswiftCore` +
   `UIKit`, símbolos mangled.
4. **Instalar no device** e abrir. É o único teste que fecha a hipótese de que
   os stubs (`Notification.Name = String`, corpos `@inlinable` removidos)
   não quebram nada em runtime — o runtime real do iOS tem as implementações,
   mas isso **precisa ser provado**, não assumido.

**Critério de aceite:** app SwiftUI/UIKit puro rodando na tela do iPhone.

### 4.4 Contar a degradação com honestidade
Documentar em `LIMITATIONS.md` o que os patches custaram:
`Notification.Name` virou `String`; `UIMenuSystem.Configuration` é struct vazio;
conformances `*Message` removidas (71+144); corpos `@inlinable` ausentes;
defaults removidos; `@objc` removido dos 25 membros das 3 classes genéricas
(→ `UICollectionViewDiffableDataSource` **não** pode ser usado como
`UICollectionViewDataSource` via ObjC — em Swift puro funciona).

## 6. Contribuição upstream (P3 — alto valor, baixo custo)

Temos um **repro mínimo e inédito** de um segfault do compilador:

```swift
// interface com -enable-library-evolution, compilado com -compile-module-from-interface
@objc open class G<T>: NSObject {   // subclasse GENÉRICA de NSObject
  @objc open func f(_ p: IndexPath) -> Int
}
```
→ `Signal 11` em `SILGenFunction::emitNativeToForeignThunk`, enquanto o **mesmo
código em `.swift` normal** produz um diagnóstico limpo
("generic subclasses of '@objc' classes cannot have an explicit '@objc'").
**O compilador aceita via interface o que rejeita via fonte, e então quebra.**

Abrir issue em `swiftlang/swift` com o repro. Benefício direto: se virar
diagnóstico em vez de crash, o próximo que tentar isso economiza dias.
