# Native intelligence / local AI

> **Status normativo:** este documento descreve capacidade de build e limites de
> runtime. Para decidir o caminho de um projeto, leia
> [`BEST-PRACTICES.md`](BEST-PRACTICES.md). Linkagem estrutural, disponibilidade
> do modelo e geração exercitada no aparelho são evidências diferentes.

This profile supports iOS 26.5 system AI without bundling model weights:

- `NaturalLanguage` / `NLEmbedding`: available today through
  `assets/NativeNLBridge.m` + `assets/NativeEmbeddings.swift`; vectors are
  generated by the OS language model and are returned as `[Double]`.
- `FoundationModels`: the native on-device Apple Intelligence API exposed by
  the iOS 26.5 `FoundationModels.framework` arm64e interface. It requires an
  arm64e module cache built from that interface; use the macro-free example in
  `assets/FoundationModelsProbe.swift`.
- `Foundation`, `Observation`, `Dispatch` and related modules remain part of
  the same explicit arm64e module graph. The old arm64 cache is rollback-only.

**Canonical arm64e matrix:** fresh IPAs cover SwiftUI/UIKit, Foundation/Dispatch,
Diffable UIKit, Swift+ObjC hybrid, CoreML/Vision/Accelerate, FoundationModels,
NaturalLanguage, embeddings, debug/StikDebug and PureSwiftKit. Each IPA is
validated as arm64e.v1/PAC before device testing.

## Evidência por camada

`FoundationModels` é capability-gated: a presença do framework no SDK ou no
link não significa que o aparelho tenha Apple Intelligence pronto.

| Evidência | O que prova | Nível |
|---|---|---|
| `FoundationModels` aparece como `LC_LOAD_WEAK_DYLIB` | o binário linka o framework sem exigir sua presença no launch | **S2** |
| `availability == .available` | este device/runtime tem Apple Intelligence disponível | **S3 do device** |
| `LanguageModelSession.respond(to:)` retorna texto | o caminho completo de geração funcionou neste cenário | **S4** |

A guarda `scripts/check-weak-link.py` é executada pela aceitação arm64e e também
tem um teste negativo: uma variante forte (`--extra-framework`) precisa ser
rejeitada. Um device sem Apple Intelligence deve reportar `unavailable`; isso é
uma condição do aparelho (região, idioma, modelo baixado), não uma falha da
skill.

## Rotas de NaturalLanguage / NLEmbedding

A rota **recomendada** é o bridge Objective-C em `assets/NativeNLBridge.m`,
usado com `NativeEmbeddings.swift` e `--extra-objc`. Ele não depende do
`swift_NaturalLanguage.swiftmodule` arm64e e, portanto, é a opção mais portátil
entre os perfis e durante a reconstrução do cache.

A rota Swift (`assets/NaturalLanguageProbe.swift`) é uma alternativa quando o
cache arm64e completo já está disponível e o projeto prefere a API Swift. Ela é
útil para validar o módulo, mas não deve ser escolhida apenas por conveniência
se o bridge atende ao caso.

## Evidência manual pendente de captura

A geração real já foi confirmada pelo usuário no cenário documentado em
`FOUNDATIONMODELS-RUNTIME.md`, elevando-o a S4 nesse cenário. Ainda não há uma
captura reproduzível com os números; em uma nova execução, registrar device,
iOS, slice, host, `availability`, prompt exato, resposta e latência em ms. Não
extrapolar esse S4 para outros devices, versões ou hosts.

## Profiles

O caminho recomendado para o LiveContainer é `scripts/build-livecontainer.sh`.
Ele é **100% local**, força o slice arm64 — compatível com iPhones arm64e — e
entrega a IPA unsigned para o LiveContainer aplicar `MH_DYLIB`, corrigir seus
load commands e reassinar com ZSign.

O modo `ISB_ARCH=arm64e` é um perfil avançado **100% local e offline**. O
linker LLD com suporte PAC do LLVM PR [#188378](https://github.com/llvm/llvm-project/pull/188378)
foi compilado para Linux/aarch64 e instalado em
`/opt/ios-toolchain/ld64.lld-arm64e`. O build normal não usa SSH, SCP nem VM;
a VM só pode ser usada uma vez para bootstrap/reconstrução do artefato.
Não habilite `Spoof SDK Version` no LiveContainer para este teste; use o
nightly/3.8.0 atual e, se necessário, ative `dontInjectTweakLoader`.


```sh
sh scripts/build-pure-ui.sh App com.example.app main.swift
```

The new profile is opt-in:

```sh
ISB_ARCH=arm64e sh scripts/build-pure-ui.sh App com.example.app \
  main.swift assets/FoundationModelsProbe.swift
```

Before using it, run `scripts/build-arm64e-modules.sh` on a real Linux host
with Swift 6.3.3 and the iOS 26.5 SDK. The resulting directory must be copied
to `/opt/ios-toolchain/foundation-build633-arm64e`. The script intentionally
fails closed until `Foundation`, `NaturalLanguage`, and `FoundationModels`
are present in that cache.

For NaturalLanguage, the bridge route works independently of the Swift
NaturalLanguage module and is useful while the arm64e Swift cache is being
built:

```sh
sh scripts/build-pure-ui.sh EmbedApp com.example.embed main.swift \
  --extra-objc assets/NativeNLBridge.m \
  --extra-framework NaturalLanguage
```

`ISB_ARCH=arm64e` agora exige o linker PAC local aarch64 em
`/opt/ios-toolchain/ld64.lld-arm64e`; não há fallback automático para SSH/VM.
A receita de bootstrap pode usar uma VM somente para compilar/copiar esse
artefato uma vez. Depois da instalação, execute:

```sh
ISB_ARCH=arm64e sh scripts/acceptance-suite-arm64e.sh
```

A solução do linker usa o suporte upstream do LLVM PR
[#188378](https://github.com/llvm/llvm-project/pull/188378), que adiciona
`ARM64_RELOC_AUTHENTICATED_POINTER`, `__auth_got`, stubs autenticados e
`LC_DYLD_CHAINED_FIXUPS` para arm64e. O LLD foi compilado para Linux/aarch64,
instalado no iSH e é chamado diretamente pelos scripts locais. O helper
`link-remote-arm64e.sh` é legado de bootstrap e não faz parte do build normal.

A suíte `scripts/acceptance-suite-arm64e.sh` comprova o caminho offline com
Foundation, FoundationModels, NaturalLanguage e o bridge de embeddings.

IPA arm64e validada de ponta a ponta:

```text
Mach-O 64-bit arm64e (caps: PAC00)
platform ios / sdk 26.5 / minos 26.5
__auth_stubs / __auth_got / __auth_ptr
LC_DYLD_CHAINED_FIXUPS
check-entry: OK
```

Uso:

```sh
ISB_ARCH=arm64e sh scripts/build-pure-ui.sh App com.example.app \
  main.swift assets/FoundationModelsProbe.swift
```

A rota local recomendada para o seu iOS 26.6 é:

```sh
sh scripts/build-livecontainer.sh MeuApp com.exemplo.meuapp \
  main.swift
```

Ela gera `arm64`, que é executável em iPhones arm64e, usa o linker nativo do
iSH e deixa a IPA unsigned para o LiveContainer aplicar o patch `MH_DYLIB` e
reassinar com ZSign. Não requer a VM.

Para `FoundationModels`/PAC arm64e nativo, a rota avançada continua:

```sh
ISB_ARCH=arm64e sh scripts/build-pure-ui.sh MeuApp com.exemplo.meuapp \
  main.swift assets/FoundationModelsProbe.swift
```

O comando acima usa diretamente o LLD PAC local aarch64 e gera uma IPA
arm64e unsigned. O erro de crash no LiveContainer não é causado pelo SDK
26.5 em iOS 26.6: o LiveContainer transforma e reassina o convidado; para
execução no LiveContainer, a variante arm64 unsigned continua sendo a rota
mais conservadora, enquanto o arm64e nativo é a rota local avançada.
